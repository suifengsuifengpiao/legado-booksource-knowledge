# 书源工坊 v1.15.18 独立审查报告（找 bug 专项）

- 审查对象：`legado-booksource-debug_v1.15.18.skill`（2026-11-02 18:24 收到的包，解包 84 文件）
- 审查方式：跑技能自带三道自检（全绿）+ 独立边界实测 + 三路并行代码审查 + 关键项复验
- 结论先行：**自带自检 96/96 全绿，但独立测试实锤 16 个 bug（高 7 / 中 4 / 低 5）**。最刺眼的是：`&&` 分隔形态归属错报、空数组静默放行、多处未捕获崩栈、以及 v1.15.18 主打的新门禁 `check_version_sync.py` 在默认调用方式下形同虚设。

---

## 一、高严重度（7 个）

### H1. `&&` 分隔的 exploreUrl：分类并 1 项 + R5 长数字归属错报
- 位置：`scripts/check_request_layer.py` R2 文本行分支（只按 `::` 切，无 `&&` 分支）
- 机理：`玄幻::url1&&言情::url2` 被当成 1 项，`url1&&言情::url2` 整串成为第一项的 url。已交付真机通过的 `shukuge_365.json` 正是此形态。
- 实测：长数字藏在第二个分类时——`[WARN·阻断] R5 [行1]「玄幻」路径含长数字段 '123456789012'`，**归属报到「玄幻」头上**（违反自家 A5 归属铁律），且 R1 报「共 1 项」。
- 参照：`references/booksource-schema.md:123` 自述支持「换行/**&&**分隔的多行 URL」——文档与实现矛盾。

### H2. `validate_booksource.py` 空数组 `[]` 静默放行（exit=0）
- 位置：`validate_booksource.py:1163-1167`
- 实测：`echo '[]' > a.json && python3 validate_booksource.py a.json; echo $?` → **0**，打印「字段完整」。
- 矛盾：空文件 exit=2、`verify/test_parse` 对 `[]` exit=2，唯独主校验器把 `[]` 当合法书源组。门禁静默通过。

### H3. `validate_booksource.py` 数组元素非对象时未捕获崩栈
- 位置：`validate_booksource.py:851`（`label=src.get(...)` 在 `isinstance` 守卫之前）
- 实测：`["x"]` / `[null]` / `[1,2]` → `AttributeError` 堆栈，exit=1（应干净 exit=2）。

### H4. `verify_booksource.py` / `test_parse.py` 纯 `null` 崩栈
- 位置：`verify_booksource.py:471`；`test_parse.py:1411`
- 机理：`json.load("null")` 返回 None 不抛异常，绕过 except，后续 `.get()` 崩。exit=1 带堆栈。

### H5. `check_request_layer.py` 遇真数组/真对象类型的 URL 字段直接崩
- 位置：`check_explore:306`、`split_options:103`（无类型守卫）
- 实测：`"exploreUrl": ["a","b"]` → `TypeError: expected string ... got 'list'`。

### H6. `<js>` 包裹的 searchUrl 被 `split_options` 误切 → 合格书源假红
- 位置：`check_request_layer.py:478`（check_search 未对 `<js>`/`@js:` 短路）
- 机理：把 JS 代码体内的 `,{`（如函数解构参数）当行内选项切出来解析 → R4 ERROR。宿主实际是先 evalJS 再 AnalyzeUrl，原始 JS 不进该解析路径。

### H7. `check_version_sync.py`（v1.15.18 主打新门禁）默认调用方式下形同虚设
- 位置：`check_version_sync.py:35`：`root = sys.argv[1] if len(sys.argv) > 1 else os.getcwd()`
- 实测：在非技能目录不带参数运行 → `[SKIP] 非技能包…：/tmp/bugprobe`，**exit=0**。定位应基于脚本自身位置（如 `self_audit.py` 用 `__file__`），且 SKIP 不应 return 0——静默放行比失败更危险。

## 二、中严重度（4 个）

### M1. R4 选项解析未走 `_gson_lenient`，同包双标
- `split_options:114-120` 直接 `raw_decode`；`{'method':'POST'}`（单引号）、`{"method":"POST",}`（尾逗号）被误判 R4 ERROR，而 R1/R2 对同形态已按 gson 宽容度放行。

### M2. `_r5_volatile` 不剥 host 与锚点 → 误报阻断级
- 实测：`https://book2024.example.com/...` → `R5 路径含长数字段 'book2024.example.com'`；锚点 `#1234567` 同样误报。判据指「路径」，host/锚点不是路径。

### M3. `check_version_sync.py` 漏比 `_meta.json` 的 display_name 版本号
- 实测：display_name 写 v1.15.17、version 仍 1.15.18 → 版本闸 exit=0「一致」，而 `self_audit.py` 3c 报 ERROR。两道门禁口径不一致。

### M4. 字段类型错误漏报（App 端会崩的形态静默通过）
- `validate_booksource.py:938` 用 truthy 判断字段"已配置"：`bookList` 写成数组/对象被放行，只报 WARN 不报错。

## 三、低严重度（5 个）

1. **charset 漏扫**：`ruleContent.content` 行内选项 `{"charset":"GBK"}` 不被识别 → 误 WARN「未见有效 charset」（`validate:999-1013`）。
2. **concurrentRate 漏检**：数字型 `30000` 静默；`20/60000` 文案把「60 秒内 20 次」误写成「间隔 20ms」（`validate:648-663`）。
3. **退出码口径**：`l0_probe.py` 坏文件 exit=0；`bypass_cf.py` 无论成败 exit=0；`check_version_sync.py` docstring 谎称有 exit=2 分支（实际只有 0/1）。
4. **打包不洁**：`scripts/__pycache__/` 被带进发布包（目录为空，无泄漏，但违反打包规范）。
5. **市场口径缺失**：frontmatter 缺 `description_zh`/`description_en`/`author`（marketplace 必填；若只走本地通道可豁免，需定口径）。另 references 有 32 处四级标题（#### ）超出层级规范；校验器报的 520 处「断链」绝大多数是行内专名（脚本名）被当路径的误报，非真断链。
