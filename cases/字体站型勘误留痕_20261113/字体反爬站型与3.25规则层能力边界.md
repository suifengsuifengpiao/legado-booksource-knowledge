# 字体反爬站型分型与 Legado 3.25 规则层能力边界

> **⚠️ 本文件为 2026-11-13 勘误版，整篇替换 2026-11-12 版。** 11-12 版关于 `www.aaawz.cc`「会话级无限动态字形 / 规则层无解 / 目录名仍不可救」的结论已证伪，请勿据旧版写书源或合并进知识库。若 11-12 版内容已并入 `references-extra/Legado_3.25_书源编写参考.md` §1.5.1，请用本版替换该子节。
>
> **性质**：补充建议稿，供引擎侧合并进 `references-extra/Legado_3.25_书源编写参考.md` §1.5（字体反爬）。书源侧不代推知识库本体。
> **证据等级**：站型判据与 `QueryTTF` 实现边界为 L1（用户提供的 3.25 反编译 `classes*.dex` + 本地抽取的 `QueryTTF.java` + `fontTools` 独立复算 + 实站 woff2 样本）；「有限置换表可解码」为**本地实站夹具 L1**（四条独立通道复算），**未做真机复验**，不写「已修复」。

## 1. 为什么必须分型，以及分型不能回答什么

抓到「乱码」时先分站型，但**站型只描述字体文件长什么样，不决定规则层能否还原正文/目录**。这两件事必须分开判：

| | 站型 A · 私有区码位重定向 | 站型 B · CJK 恒等 cmap + 字形轮廓替换 |
|---|---|---|
| cmap 特征 | 含 `U+E000~F8FF` 或 `≥U+F0000` 私有区码位 | **无私有区**；码位集中在 CJK 基本区，字形名 `uniXXXX` 与码位恒等自洽 |
| 混淆发生在 | cmap 映射（码位 → 字形） | `glyf` 轮廓重绘 / 重排（码位本身没变） |
| 抓到的正文 | 私有区乱码字符 | 正常汉字字形，但字形与 Unicode 不对应 |
| 字体 API 通道 | 可反推 `replaceFont` / `replaceRegex` 映射 | **不适用**（见 §3 三条限制） |
| 规则层能否还原 | 通常能 | **未判定，与站型无关**（见 §4、§6） |
| `reverse_font.py` 判定 | `pua_codepoint_redirect` / `rule_layer_recoverable=True` | `glyph_shape_cjk_identity` / `rule_layer_recoverable=None` |

只认站型 A 的诊断会把站型 B 报成「可能非加密字体」（假阴性），这是 v1.15.24 工具侧修复的起因；而把站型 B 直接判成「规则层无法还原 / 目录名仍不可救」是**从字体形态越界推断业务结论**，已在 v1.15.25 更正。

## 2. 官方通道（3.25，现状）及其适用边界

```javascript
var f1 = java.queryBase64TTF(b64[1]);
var f2 = java.queryTTF("https://.../Source Han Sans CN Regular.ttf");
return java.replaceFont(result, f1, f2, true);
```

（引自 `references-extra/Legado_3.25_书源编写参考.md` §1.5。字体相关 API 名单 `queryTTF` / `queryBase64TTF` / `replaceFont` 可在 3.25 `classes*.dex` 字符串池定位；`official-help/ruleHelp.md:180-182` 有同源示例。）

**关键边界**：官方 §1.5 只定义**这三个字体 API**，**没有任何官方条文说「规则层不能做字符串置换解码」**。规则层还有一条完全不经过字体 API 的通道——`jsLib` 内置置换表 + `<js>` 规则逐字查表解码（见 §4）。把 §3 的三条限制外推成「规则层无解」，是书源侧此前的错归因，不是官方结论。

## 3. `QueryTTF` 的实现边界（3.25 反编译本体）

依据：本地 3.25 `classes*.dex`（`strings` 可定位 `QueryTTF` 内部类、`sfntVersion` / `numTables` / `glyphToUnicode` / `getGlyfByUnicode` / `getUnicodeByGlyf` 等字段与方法名）+ 抽取的 `QueryTTF.java`。

1. **格式**：构造函数按手写 TTF 表目录解析 —— `sfntVersion`、`numTables`、`cmap`、`loca`、`maxp`、`glyf`。**没有 woff2 解码分支**。dex 字符串池里的 `font/woff2` / `woff2` 位于 MIME / 邻近字符串，不是 `QueryTTF` 的解码路径。站点只发 `wOF2`（woff2）时，必须先由外部转成标准 TTF（`\x00\x01\x00\x00`）才可能进这条通道。
2. **匹配口径**：`getGlyfById()` 把简单字形轮廓序列化成 `x,y|x,y` 坐标串；`glyphToUnicode` 是**精确 HashMap 匹配**（`glyphString → codepoint`），无容差、无相似度阈值。`replaceFont` 依赖「混淆字体的轮廓串」能在「正确字体」里找到**完全相等**的键。轮廓一旦重绘、重排或量化即失配。
3. **字形集合可随会话变**：字形集合可锚在会话级 guard cookie（如 `reader_guard_id`）上，每次会话下发不同字库；跨会话轮廓集合变化。

> **这三条只封闭 `java.queryTTF` + `java.replaceFont` 这条字体 API 通道。** 它们**不封闭**规则层的纯字符串置换解码通道——后者只处理响应体里的字符串，不解析字体、不调用任何字体 API。三条成立时结论是「别在这条通道上继续调 XPath / 换字体 API / 截正则」，**不是**「规则层无解」。

## 4. 实站取证（`www.aaawz.cc`）：有限 16 套固定字符置换表

11-12 版在此处下的结论是「会话级动态字形 ⇒ 规则层无解，目录名仍不可救」。该结论已被证伪。

### 4.1 哪些现象是真的

- 响应头 `x-content-guard: glyph`、cookie `reader_guard_id`、正文 JSON 内 `font:{family,url:'/static/fonts/<48hex>.woff2'}`。
- 四份 woff2 样本：`magic = b'wOF2'`；用 `fontTools` 转存标准 TTF 后，`cmap` 均为 **6763 个 CJK 基本区码位恒等映射**（`uniXXXX` 与码位自洽 6763/6763）。混淆不在 cmap，在 `glyf` 轮廓。
- 跨会话轮廓精确交集 80 / 6763 = 1.18%，按坐标量化容差 `q=2/3/5/10` 分别只到 `3.74% / 5.54% / 15.90% / 40.72%`；每份字体 `name[1]` 家族名随机。
- 这些**都是真的**，但属于**渲染层**：说明「浏览器显示时，字形轮廓每会话重排」。

### 4.2 错在哪

把「渲染层每会话下发不同字体文件」直接等同于「**字符置换关系**每次会话都变」，并据此下发「静态映射表必失效 / 规则层无解」的禁令。**字体文件的形态 ≠ 字符置换关系。**

实站真相：站点使用**有限 16 套固定字符置换表**轮换；`font.url` 文件名前 **12 位**即表号。每张表长 6763，是 `AA_CODES`（6763 个唯一 CJK 字符）的完全双射；16 表两两不同，同一下标在 16 表给出 16 个不同字。规则层按表号查表逐字解码，即可同时还原正文与目录名。字体轮廓可以每会话变，但乱码字与正确汉字的对应关系固定在这 16 张表里。

### 4.3 四条独立通道复算（本地实站夹具 L1）

| 通道 | 做法 | 输出 |
|---|---|---|
| A | Python 换语言重写解码，**不执行别家 JS**，只取两张常量表 | 16 表结构如上；历史实站抓到的 **5/5** 个字体 key 全部命中 16 表；`session_text.json` 乱码正文解成《十日终焉》开篇；1496 条目录**全量解码失败 0/1496** |
| B | Node 执行别家 AI **原始 `jsLib` 的 `aaDecode` 本体** | 与 A 一致（解码前「驳忠溺狄揶灞推睽肭溪…」→ 解码后「一个老旧的钨丝灯被黑色的电线悬在屋子中央…」） |
| C1 | Node 端到端跑 **`ruleContent.content` 规则本体**，用真实乱码正文构造 `result` | 解出通顺正文，判定正确 |
| C2 | Node 端到端跑 **`ruleToc.chapterList` 规则本体**，喂真实 1496 条目录响应 | 1496 条全解出；`[0] 第1章 空屋`、`[748] 第749章 皆是蝼蚁`、`[1495] 陈俊南（终）`；残留乱码特征字符 **0/1496** |

解码骨架（ES5，可放 `jsLib`）：`AA_CODES` 作码位索引表，`aaFontKey(u)` 取 `u` 末段文件名前 12 位，`aaDecode(fontUrl, s1)` 按 `AA_TABLES[aaFontKey(fontUrl)]` 逐字查表；无表 key 时**原样返回乱码**（降级兜底，不要硬凑）。外层响应为 LZString `compressToBase64`，正文 `content` 内层再套一层，需先解压再解码。目录规则从详情响应取 `tid/siteid`，再 `java.ajax` 取章节列表，用 `cl.font.url` 解码 `chapters[].title`。

> **证据等级说明（如实）**：上表数字来自书源侧会话内对实站响应的本地实跑；字体样本与脚本**未随本材料包**（会话级样本无法固化）。标 L1 的是 dex 本体 + `fontTools` 独立复算这一**判据**与四条独立通道互证，数字本身属「本地实测、样本未随包」，不包装成已交付证据。需要复算时按 §4.4 片段自取同站字体重跑。

### 4.4 自包含复算片段（只需 `fontTools` + 两份同站不同会话的 woff2）

```python
from fontTools.ttLib import TTFont

def glyph_sig(path):
    f = TTFont(path)
    cmap = f.getBestCmap() or {}
    glyf = f['glyf'] if 'glyf' in f else None
    out = {}
    if glyf is None:
        return out  # CFF/OTTO 无 glyf 表，与 QueryTTF 口径不同源
    for cp, gname in cmap.items():
        g = glyf[gname]
        coords = getattr(g, 'coordinates', None)
        if coords is None:
            continue
        out[cp] = tuple((int(x), int(y)) for x, y in coords)
    return out

a, b = glyph_sig('session_A.ttf'), glyph_sig('session_B.ttf')
exact = {cp for cp in a if cp in b and a[cp] == b[cp]}
print('精确交集', len(exact), '/', len(a))
```

**判读（勘误后）**：精确交集占比极低 ⇒ 字形轮廓每会话重排 ⇒ **字体 API 通道不适用**。这一步**推不出**「站型 B 且会话动态 ⇒ 放弃规则层还原」；必须另做 §6 的字符置换通道取证。

## 5. 未实测 / 受限边界

- **16 套表覆盖性未证**：本地只抓到 5 个字体 key，全部命中 16 表；不能证明站点永远只发这 16 套。别家 `aaDecode` 对无表 key 原样返回乱码，自带降级兜底。
- **搜索／详情层**：端到端只覆盖 `ruleContent` 与 `ruleToc`；`ruleSearch` / `ruleBookInfo` 未用真实响应端到端复跑；该站发现页不启用。
- **harness 近似**：C1/C2 用 `new Function` 包裹取返回值，≠ 真机 Rhino 绑定；规则原文末句是裸表达式，与 3.25 表达式上下文一致，但**未做真机复验**。
- **整体可用性**：完整书源能否在真机 3.25 导入即用，**未做真机复验**；证据等级为本地实站夹具 L1，不写「已修复」。
- 未验证其它 Legado 构建是否支持 woff2 —— 本结论**只针对用户 3.25 反编译**，不外推。
- 对照用的 `Noto Sans CJK` 为 CFF/OTTO（无 `glyf` 表），与 `QueryTTF` 的 `glyf` 解析口径不同源，相关对照结论标「未实测/受限」，不外推。
- `classify_font_obfuscation` 一类判据是**启发式**：只识别站型，不等于证明加密，更不等于判定规则层能力；「是否会话动态」须取多份样本比对，工具不自动下结论。

## 6. 给写书源的人的操作顺序（勘误后）

1. 遇到「乱码 / 看不懂的汉字」→ 先取字体文件，跑 `reverse_font.py <字体文件>` 看 `obfuscation_type`。
2. `pua_codepoint_redirect` → 走 §1.5 既有 `replaceFont` / `replaceRegex` 通道。
3. `glyph_shape_cjk_identity` → **不要在字体 API 通道上继续调 XPath、换字体 API 或截正则**；但**不要据此写「规则层无法还原」或放弃目录**。转 §3 的第 4 步。
4. **另查字符置换通道**（这一步是关键，11-12 版缺的就是它），三条任一成立即可在规则层还原，**包含目录名**：
   - ① 正文／目录乱码是否来自**有限套固定置换表**（同一 `font.url` 是否对应固定映射）；
   - ② 表是否随响应下发，或可按 `font.url` 前若干位（实站为 12 位）索引到表号；
   - ③ 是否能在 `jsLib` 内置表，并由 `<js>` 规则对 `ruleContent` / `ruleToc.chapterList` 逐字查表解码。
5. 查不到置换表、也没有其它字符串映射线索时，才写「本规则层无法还原」并转浏览器阅读／换源——**且必须写明是「此站此通道取证后」的结论，不是站型推论**。
6. 单份字体只能判站型；要判「会话动态」须取多份同站字体按 §4.4 片段复算。
7. 凡书源含 `<js>`（尤其 `searchUrl`），须真机或 Rhino 直 eval 表达式复核，不能只信 `node --check` / `new Function`（表达式上下文里 `return` 会报 `invalid return`）。
