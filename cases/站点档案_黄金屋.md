# 黄金屋（huangjinwu.org）书源站点档案

> 关联书源：🄼黄金屋（v3 修复版，真机已验证通过，目录 `(1/998)` 全加载）
> 记录日期：2026-10-07
> 用途：下次遇到同类「Cloudflare 按端点盾 + 目录 ?page=N 分页（越界钳末页）」站点，直接参考，避免重踩 `nextTocUrl` 取尾页的坑。

## 一、站点与入口架构
- 首页 `https://www.huangjinwu.org/`，纯静态 HTML + `og:` meta，无客户端加密、无 JS 渲染正文。
- **搜索是站内唯一被墙的入口**：`/search?keyword=X` 被 **Cloudflare 五秒盾**拦截，直连返回"正在检查您的浏览器"挑战页（空壳，列表 0 条）。
- 其余入口（首页 / 分类 `/list/N/{{page}}.html` / 标签 `/tag/N/{{page}}.html` / 排行 `/rank/N/{{page}}.html` / 详情 / 目录 / 正文 / `robots.txt`）均 200 明文直连，正常。
- 发现页 `exploreUrl` 由 `@js:` 拼装：排行榜 9 项 + 分类 9 项 + 标签 20 项，URL 形如 `/rank/{r}/{{page}}.html`、`/list/{i+1}/{{page}}.html`、`/tag/{r}/{{page}}.html`。

## 二、关键坑 ①：Cloudflare 按「端点」触发（只给搜索上手段）
> 与"全站 webView"不同：本类站**只有 `/search` 一个路径被 CF 挑战**，其它路径直连明文。
> 切忌把 `webView` 加在 `chapterUrl` / `bookUrl` 上（每章多等数秒，代价 100×）。

- 判据：逐入口取证——`/search` 抓到 CF 挑战页、`/` 与 `/list/1/1.html` 都是明文 ⇒ **只给 `searchUrl` 内联过盾**。
- 修复：
  ```
  searchUrl: "/search?keyword={{key}},{\"charset\":\"utf-8\",\"webView\":true,\"webWait\":12000}"
  ```
  `webView:true` 走内置浏览器过盾、`webWait:12000` 等够 CF 放行（默认 ~1000ms 不够，会取空）。
- 配套：`enabledCookieJar:true` + 真机先过一次 CF 落库 Cookie，后续搜索复用。

## 三、关键坑 ②：`checkKeyWord` 只是调试关键字，绝不过滤真实结果（纠偏）
- 经 3.25 反编译 `booksource-schema.md` / `field-availability.md` 实证：`ruleSearch.checkKeyWord` 是**「校验书源用的测试关键字（调试用）」**，只在 App 的"校验书源"流程里当样例词，**不参与真实搜索结果过滤**。
- ⚠️ **本档案纠偏**：早期曾误判"残留 checkKeyWord 会过滤掉不含该词的结果→搜索恒 0 条"，**这是错的**。搜索恒 0 条的唯一真凶是 `/search` 的 CF 盾（见坑 ①）。`checkKeyWord` 残留删掉只是清理调试残留，与 0 条无因果。
- 技能铁律里**不要**写"checkKeyWord 会过滤结果"——那是错误机制。

## 四、关键坑 ③：`nextTocUrl` 取「分页条最后一个链接（尾页）」而非「下一页」→ 跳页丢章
> 本案最隐蔽的坑，也是 998 章书只拿到 ~298 章的根因。

**症状**：目录翻 1~2 页后，章节数停在某中间值，后面全丢（读者目录显示 `(1/298)`，实际 `(1/998)`）。

**根因**：原 `nextTocUrl` 写成
```
.page-link:last-child@href
```
分页条里 `.page-link` 是一组链接：**首页 / 上一页 / 1 / 2 / … / 下一页 / 尾页**。`last-child` 取到的是**整条分页里的最后一个链接（尾页）**，不是"下一页"。于是：第 1 页 → 抓到尾页（如第 10 页）→ 再翻又到尾页，中间的 2~9 页全部跳过。

**铁证**：读者端目录 `(1/298)` vs 详情页 `共998章`；修复后真机目录 `(1/998)` 全加载。

**修复：纯 JS 按页码确定性递增（末页返回空串自然停止，防回环）**：
```javascript
@js:(function(){
  var h=''+result, u=''+baseUrl, out='';
  // 1) 优先找"下一页"链接（分页条里紧邻"下一页"文字的 href）
  var mm=h.match(/<a\b[^>]*href\s*=\s*["']([^"']+)["'][^>]*>(?:(?!<\/a>)[\s\S]){0,80}?下一页/);
  if(mm&&mm[1]){ out=mm[1]; }
  else {
    // 2) 否则按页码递增：当前页从 baseUrl 的 ?page=N 取；目标页 = cur+1
    var cur=1, max=0, has=false, pm=u.match(/[?&]page=(\d+)/);
    if(pm){ cur=parseInt(pm[1],10)||1; has=true; }
    var nr=/[?&]page=(\d+)/g, v;
    while((v=nr.exec(h))){ var n=parseInt(v[1],10); if(n>max){max=n;} }
    var nx=cur+1;
    if(max>=nx){ out=has ? u.replace(/([?&]page=)\d+/,'$1'+nx)
                          : (u+(u.indexOf('?')>-1?'&':'?')+'page='+nx); }
  }
  return out;
})()
```
**为什么不能靠"越界判定"终止**：本站 **越界页（`?page=6` 超出实际 5 页）被服务端钳到末页**而非 404，故"是否越界"无法作为终止判据；必须以"页面上是否还存在下一页链接"为准（上面的 `max>=nx`）。末页无下一页 ⇒ `out=''` ⇒ Legado 自然停止，不死循环。

## 六、翻页机制
- **目录**：`?page=N`，**每页 100 章**，本书 998 章 = 10 页。越界页被钳到末页（见第四节）。
- **正文**：`#readerContent` 单页正文；跨页靠 `nextContentUrl = a:matches(下一页)@href` 拼接。
- **搜索/发现**：`{{page}}` 走 `webView` 过盾 / 直连，无需特殊翻页逻辑。

## 七、UA / header
- 全局 `header`：`{"User-Agent":"Mozilla/5.0 (Windows NT 10.0; Win64; x64)...Chrome/120.0.0.0","Referer":"https://www.huangjinwu.org/"}`，JSON 格式（行格式会被 App 整段丢弃回落默认 UA）。
- 本站对桌面/手机 UA 未做差异化（不像 3Q中文网只给手机 UA），桌面 UA 即正常。

## 八、书源实现要点（Legado 3.25）
- 净化一律放 `content` 的 `<js>` / `##正则##`；`ruleContent.replaceRegex` 是死字段（3.25 零消费点），写了不执行。
- 解析规则 `<js>` 必须 IIFE 包裹 `(function(){...})()`，否则顶层 `return` 报 `invalid return`。
- 内嵌 JS（nextTocUrl 的 `@js:`）交付前必过 `validate_booksource.py` + `js_layer_check.py`，语法错会本地绿、真机挂。
